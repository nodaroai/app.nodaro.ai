Video Overlay layers can carry a video. A layer takes exactly one of `imageUrl` or `videoUrl`; a video layer can have `sound: { volume }` (0 to 1) and fades in and out only when `animate` is set. A request is refused with `layer_two_sources` for a layer with both, `too_many_video_layers` past 2 video layers, and `sound_without_video` for sound on an image layer that carries its own `imageUrl`; on a wired slot whose wire is an image at run time, `assembleVideoOverlayRequest` skips a stored `sound` instead, so the run goes ahead. `videoOverlayWiredLayerKind({ type, handle, declaredMediaType }, url)` tells whether a wired source is an image or a video: the medium its pip or declared port carries first, then a single-medium producer, then the URL's extension, else an image; the video pips of the producers that hand on a video or an audio file (Adjust Volume, Pitch & Tempo, Voice Changer, Voice Changer Pro, Dubbing, Split Media) are videos whatever their file is named. `declaredOutputMediaType` reads the medium a component or sub-workflow port declares, and `listColumnMediaType` a List column's type (`image-url`, `video-url`), which ranks below the URL's extension: a `.png` stays an image in any column, and the column type decides only a link with no recognisable extension, and `videoOverlayHasVideoLayer` tells whether a request has any video layer. The assembly drops an empty-string `imageUrl` or `videoUrl`. A video layer that names a preset but no `start` starts at 0, as the default layer does (an image layer without one is still refused). `normalizeVideoOverlayNodes` stores a wired slot's layer with only the `animate` it was written with — its default follows the wire's kind, which is read at the run, so a video wired in later does not fade — and `withoutImpliedVideoOverlayAnimate` is that rule for any other writer.

The base video can be placed with `baseBox` (a layer's box: `anchor`, `x`, `y`, `width`, `height`, `fit`; needs an `outputAspect`). On the request it is a `VideoOverlayBaseBoxSpec`: `anchor` and `width` are required, `x` and `y` default to 0 and `fit` to contain; `ExpandedVideoOverlayRequest` carries the box as stored or sent (`Partial<VideoOverlayBox>`), and the render fills the rest. A request can name a `layout`: `video-bottom`, `video-top`, `stack-whole`, `stack-filled` or `pip`. `expandVideoOverlayLayout` writes a layout's boxes, `resolveVideoOverlayStackRects` and `resolveVideoOverlayBaseRect` give the stacked and placed rects, and the new refusals are `base_box_needs_aspect`, `layout_needs_aspect`, `layout_needs_video_layer` and `layout_conflicts_base_box` (a stack layout places the base itself, so it takes no `baseBox`). `videoOverlayCompositionKey` takes the wired slots that are videos (`videoSlots`), so a wire whose kind changes while its link does not marks a result old; a node with no wired video keeps its key. An empty `layout` reads as none, and `assembleVideoOverlayRequest` drops a stored base box's `null` fields, which every reader treats as absent. `clampVideoOverlayAspect` holds a video's aspect between 1:8 and 8:1 (`VIDEO_OVERLAY_ASPECT_BOUNDS`) before it is placed, and `evenVideoOverlayRect` rounds a video's rect down to the even pixels the render draws, so a preview and the render place a video identically; `placeVideoOverlayVideos` is that one placement of the base and every video layer (a stack, a base box, each video layer's own box), which both the render and the canvas preview call.

A run with a video layer takes a base of at most 60 s (`VIDEO_OVERLAY_VIDEO_MAX_BASE_SEC`), at most 2 video layers and a layer video file of at most 200 MB (`VIDEO_OVERLAY_MAX_LAYER_VIDEO_BYTES`). Its price: `videoOverlayCreditId(hasVideoLayer)` names the row — the flat `video-overlay` row for an image-only run, or `video-overlay:video` when any layer is a video — and `videoOverlayVideoUnits(baseSec)` the units of the video row, one per started 5 s of the base (a base not known yet counts the 60 s cap, 12 units). `videoOverlayBaseTooLong(baseSec)` tells a base past the cap, on the same priced seconds, and `VIDEO_OVERLAY_PRICING` holds the ids, the unit and the cap. `VIDEO_OVERLAY_REMEASURE_SLACK_SEC` (0.5) is how much longer a base may measure when it is rendered than when the run was priced, before the render refuses it as changed. `videoOverlayWireMediumBeforeRun(source, { target, knownUrls })` tells what a wired source hands a Video Overlay before the run — `image`, `video`, or `unknown` when its content follows a file not known yet — by the same rule on a layer handle; on the `layerPlan` handle only a plan pip answers `image` (UGC Cards' plan is its card images).

`@nodaro/sdk`: `client.media.videoOverlay` sends video layers (`videoUrl`, with `sound: { volume }`), `baseBox` (only `anchor` and `width` are required) and `layout`. Its request is `VideoOverlayRequest` from `@nodaro/shared/video`, whose layer type takes `imageUrl` or `videoUrl`, never both; the method's documentation covers video layers, sound, the base box, the five layouts and the price of a run with a video layer.

`@nodaro/cli`: `nodaro media video-overlay` takes `--layout <id>` (`video-bottom`, `video-top`, `stack-whole`, `stack-filled`, `pip`) and `--base-box <json>` (a layer box as a JSON object; it needs `--aspect`). Video layers come through `--layers-file`: an entry with `videoUrl` instead of `imageUrl`, and `sound: { volume }` to mix its audio in. Positional layer URLs stay image layers.
