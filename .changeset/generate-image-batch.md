Several images in one generate-image call. `GenerateImageParams` types `count` (1–4 images, each its own job) and `models` (the same request on 2–4 image models instead of `provider`; with `count`, per model, at most 8 images), plus `seed` (image i gets `seed + i`) and `userPrompt` (the prompt as your user typed it — stored on the job, never sent to the model). With a literal `count` above 1 or `models`, `nodes.run("generate-image", …)` is typed to answer `GenerateImageBatchResult` — every job id grouped by model (`jobIds`, `groups` with credits and per-model corrections, `batchId`, `totalCredits`); the batch is checked against the balance and charged as a whole or not at all, and with an `idempotencyKey` each image is keyed `<key>:<i>` so a retry returns the same jobs. The new `nodes.runBatchAndWait("generate-image", params, opts)` submits once and waits for every job, resolving `{ batch, results }` with one `BatchJobOutcome` per job, so one image failing never discards the others. `runAndWait` and `runMany` now refuse a batch request before anything is sent (`batch_requires_run_batch_and_wait`) instead of silently waiting for its first job. `jobs.list({ batchId })` lists a batch's jobs. `origin` and `sessionId` (`GenerationSessionParams`) are now typed on every generation params type — video upscale / depth / narrated video, the 3D scene params and the character / object / location / creature generate inputs — since the platform stamps them on every job-creating request; an `origin` that is not a slug is refused with a 400. The CLI's `nodaro nodes run generate-image` takes `--count` and `--models`, prints the job ids grouped by model, and `--watch` follows every job of the batch.
